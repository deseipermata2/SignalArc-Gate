## Implemented read-only registry boundary

`server/sg07/registry.ts` exposes an explicit server-owned policy and `createRegistryReader`; it has no default endpoint, signer, environment credential lookup or write RPC. Required policy: chain 8453, native USDC, valid nonzero registry address, approved nonzero runtime-code hash, **finalized** block policy, explicit minimum confirmations (1–100000) and maximum block age (1 second–1 hour). Those validation ranges are not an approved production policy. The local fixture values are only simulation inputs; no policy/address was inserted in application configuration.

The reader derives UUID/original-owner namespaced ID using SG-04's existing ABI encoding, checks current-owner/payout/atomic price/configuration hash/version/enabled expectations and rejects pending/accepted transfers. It checks `eth_chainId`, obtains finalized/latest block metadata, enforces depth/age/future-clock limits, pins `eth_getCode` and both `eth_call` operations to `{blockHash, requireCanonical:true}` (EIP-1898), compares approved runtime hash and contract `CHAIN_ID`, strictly decodes the actual seven-field getter tuple, then rechecks the canonical numbered block/hash/timestamp. Missing, unsupported EIP-1898/finalized behavior or contradictory provider data fails closed; there is no latest/number-only fallback. A malicious/incorrect RPC can still lie: this is a trusted-provider observation, not an independently verified state proof or a guarantee against a later reorg/change.

`registryExpectation` reads server D1 resource/merchant/binding data through a prepared UUID query, requires existing onchain-confirmed binding fields/address/freshness, validates the resource, rederives ID and recomputes commitment. It writes nothing and never accepts a client observation. A database provenance label alone does not establish canonical deployment. No admission/synchronization service is implemented. The current negative integration check proves missing bindings fail against actual D1; a genuine admitted D1-to-live-registry path remains unverified. Configuration can change after any read; production orchestration must retain D1 revision/generation CAS and revalidation near settlement and release.

`server/sg07/rpc.ts` provides a fixed server-selected HTTPS endpoint plus injected transport, with only four read method names. It has no global-fetch fallback and rejects query-string endpoints, unsafe URLs, redirects/non-200 status, mismatched JSON-RPC IDs, error-plus-result, malformed/oversized JSON and slow reads. Response streaming is capped at 128 KiB, strings/structure bounded before ABI decoding; per-call deadline 2 seconds and reader deadline 5 seconds include elapsed-clock checks. Underlying transport cancellation is cooperative; failure never grants access. The actual RPC provider/credential transport and its connection trust require separate approval. No live endpoint was contacted.

## Facilitator boundary and settlement safety

`server/sg07/facilitator.ts` accepts an injected client structurally typed from the installed public `createCdpFacilitatorClient` return type. It never invokes that factory, reads credentials or provisions a wallet. Existing compatibility tests still load/invoke the helper's explicit empty-credential guard inside workerd. SDK versions remain core/EVM/extensions **2.29.0**, SVM **2.28.0**, CDP **1.60.0**.

The new boundary validates exact EVM, Base/native USDC, positive atomic price, server payout, EIP-3009/upfront requirements; reuses the bounded SG-05 exact challenge/header parser; enforces freshness; and requires valid verification with matching payer before creating a closure-owned opaque permit. It consumes that permit once, checks authorization freshness again and requires a successful server-supplied **durable pending-claim callback** before settlement. A WeakSet is only an additional in-process guard, not durable idempotency; production callers must bind the callback to the existing D1 authorization/configuration CAS. All production wiring remains absent.

The fixture proves one settle call under concurrent permit submissions using a real local D1 compare-and-set. It signs an unfunded ephemeral local EIP-3009 authorization in Node memory, and the isolated mock cryptographically recovers it in workerd. No blockchain transaction is signed/broadcast; no key leaves Node or is logged/persisted. The fixture's settlement reply is explicitly simulated. Exceptions, deadline overruns, malformed/rejected/conflicting replies produce `settlement_unknown`, with no automatic retry. Even a coherent success becomes only `reported_settled`, never a confirmed receipt/content release. No client transaction hash is accepted as proof.

Important limitations: this boundary is an integration component, **not a complete production gateway**. Reused SG-05 challenge metadata is still explicitly local simulation metadata. CDP HTTP decoding occurs inside the SDK before these returned-object bounds; raw CDP HTTP parsing/timeout/retry behavior needs review/remediation before use. The adapter does not provide cancellation guarantees for SDK calls or an authoritative reconciliation source. It cannot replace the SG-05 durable workflow, independently certify settlement, enable production metrics or make the existing local-only gateway deployable. No default client or publicly selectable mock exists.

SG-05 state machine/store/reconciliation code was preserved. Created→verifying→verified→settlement_pending uses durable uniqueness/CAS, pending interruption becomes unknown, and unknown may resolve only from authoritative evidence. Terminal failures cannot reset to payable. Receipt/analytics persistence is atomic in the local tests; a distributed transaction across facilitator/D1/upstream does not exist. At-most-one release claim is not confirmed client receipt. Paid-but-unfulfilled recovery/refunds remain policy and implementation blockers; no refund function or automatic retry was invented.

## Upstream, clocks and operations

`server/sg07/upstream.ts` explicitly validates then rejects every production destination with `connection_safe_transport_unavailable`. It performs no DNS lookup or fetch. Private/IP/metadata/alternate-IP/rebinding-looking URLs and even ordinary public hostnames cannot pass. This is proof of **disabled egress**, not proof that arbitrary-host DNS rebinding is solved.

Official Cloudflare Request docs describe `resolveOverride` as a hostname override with same-zone constraints; it does not expose or certify the actual remote peer address to this code. An independent DNS check can race the actual connection. A future narrowly restricted owner-controlled hostname/service route may be reviewable within the stack, but ownership, DNS/TLS, redirects and connection behavior need evidence. No such host, service binding or DNS configuration is supplied or silently introduced. Arbitrary merchant upstream execution remains blocked. Existing GET-only/no-buyer-headers, redirect rejection, no-store, content-type, stream/JSON limits and late-body checks remain tested only through isolated SG-05 transport.

Production `Date.now`/timer scheduling and CPU budgets are not established by local clocks. The new APIs require an injected trusted clock and do not claim an ambient clock source solves the issue. Existing nonce limits and bounded reporting windows are not global rate limiting. No production request/concurrency limiter, retention scheduler, alerts or operator interface was added. New modules log nothing; public error/bundle isolation tests assert no mock/provider diagnostic leakage. Authentication/merchant reporting remains unchanged and no sensitive tokens are added to analytics.
